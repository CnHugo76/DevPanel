> 契约：v1.3-A ~ v1.3-D 已由用户确认并生效（2026-10-21），见 `contract/api.md` §13–§16 与 `packages/contract`。

## 0. 定位

v0.1 ~ v0.3 证明了“人和 AI 共用同一个运行入口”可行。但这一点已经不独特：市场调研（[market-research-2026-10-21](market-research-2026-10-21.md)）列出的 Pier、lpm、Candle、DevWebUI 都在做。v0.4 把定位收紧为：

> **本地运行状态的单一事实来源：AI 能可靠地读写它，人能监督和接管它。**

据此，v0.4 **不增加新的视图**（不扩 Maven、不扩 Git），只补两类缺口：

- **AI 闭环**：启动后“起来了没有、哪里报错”要一条命令得到确定答案，不靠 agent 自己翻日志、猜就绪行。
- **人的监督**：知道每个动作是谁做的；需要时让管理服务替人挡住 AI，而不是只靠 skill 里的文字约定。

外加一项不改功能、但决定能否被别人用起来的工作：**让别人能从 GitHub 下载并用起来**。

## 1. 本版目标

| 问题 | v0.4 的回答 |
| --- | --- |
| `running` 只表示进程还在。AI 要自己 `logs --tail 200` 找 `Started … in …`，费 token、判断不一致 | **就绪条件**：AI 注册时定义，管理服务判断；`--wait-ready` 一条命令返回是否就绪、用时和出错摘要 |
| AI 读日志只能整段拉取，大部分是无关输出 | **日志摘要**：错误块、折叠堆栈、合并重复、最后几行，按字节预算返回；支持增量读取 |
| 面板看不出服务是谁启动、谁停止的；AI 无法区分“用户停的”和“另一个 agent 停的” | **操作来源**：每次操作、每次运行、每次停止都记录发起方（你 / 某个 AI / 命令行），项目有一条“动态”时间线 |
| “用户停止后不要自动重启”“强制停止先问用户”只写在 skill 里，全靠 agent 自觉 | **托管规则**：由管理服务执行的“停止后暂停”“锁定服务”“AI 不得强制停止”，只能在界面上修改 |
| 安装要 Node 24 和源码仓库，别人很难装起来 | **GitHub 下载**：Releases 提供内含管理服务和 CLI 的 App 压缩包，也可以按 README 从源码构建 |

## 2. 就绪

### 2.1 是什么

就绪 = “这个服务已经可以接受请求”的一个**可观察信号**，例如日志出现 `Started DemoApplication in`，或进程开始监听端口。它**不是**健康检查：不判断业务是否正确，也不在就绪之后持续探测。v0.1 §14 “不做业务健康检查”继续有效。

服务状态（`running` 等）不变。就绪是挂在每次运行上的另一层信息：进程还在 ≠ 已就绪。

### 2.2 就绪条件（AI 定义）

AI 在注册 / 更新项目时，为每个服务可选地登记一个就绪条件，二选一：

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| 日志包含 | 本次运行的输出中出现任一给定文字（区分大小写，去掉 ANSI 后匹配，最多 5 条，每条 ≤ 200 字符） | `Started DemoApplication in`、`Local:`、`ready in` |
| 端口监听 | 本次运行的受管进程开始监听 TCP 端口：指定端口，或任意端口；端口可以引用数字选项 `${port}` | `8080`、`${port}` |

另有等待上限（默认 120 秒，1–900）。

日志条件只用纯文字，不用正则：AI 写得出、人看得懂，也没有正则回溯失控的风险。端口条件沿用 v0.2 的真实端口来源：只看已核验受管进程的监听套接字，不扫描其他进程。

未登记就绪条件的服务照常运行，只是无法回答“是否就绪”。

### 2.3 规则

- 每次运行独立判断：`等待中 → 已就绪`，或 `等待中 → 未就绪（超时）`，或 `等待中 → 就绪前已结束`。已就绪的运行之后**不再检查**。
- 超时只做标记，**不停止、不重启**服务。自动重启仍不做。
- 记录就绪时间与用时（相对启动时刻），以及证据：匹配的日志行号或端口。运行记录保留这些信息，可以对比“这次比上次慢了多少”。
- 管理服务重启后，仍在等待的运行继续检查后续日志与端口；无法续接时标为未知，不猜测。
- 修改就绪条件只影响下次启动，与其他配置一致；`configChangedSinceStart` 不因就绪条件变化而标记（它不影响进程本身）。
- 项目级启动仍按配置顺序启动，**不等待前一个服务就绪**。服务依赖编排仍不做。

### 2.4 AI 怎么用

```bash
devpanel restart <project-id> --service backend --wait-ready --json
```

命令先等操作完成，再等每个目标就绪。输出一份启动报告：每个服务的操作结果、就绪状态与用时、实际端口。未就绪或就绪前退出时，附带该运行的日志摘要（§3），agent 不必再单独读日志。

| 情况 | 退出码 |
| --- | --- |
| 全部已就绪 | 0 |
| 有服务就绪前退出（操作失败或进程自行结束） | 1 |
| 有服务超时未就绪 | 11（新） |
| 服务未登记就绪条件 | 0；报告中标为“未配置”，并在 stderr 提示 agent 自行确认，或通过更新配置补上就绪条件 |
| CLI 等待到期，但管理服务还没下结论 | 8（沿用） |

agent 接入新项目时，应当同时登记就绪条件（写入 skill 的 onboarding 指引和 `project rules` 文本）。

### 2.5 界面

- 服务状态旁显示就绪：等待中（动态标记）、已就绪（悬停显示“启动后 12.3 秒就绪 · 依据：日志第 214 行”）、未就绪（琥珀色）。
- 编辑项目时，每个服务多一个“就绪条件”分区：类型、文字或端口、等待上限。
- 未就绪超时：窗口不在前台时发通知，例如“reg-radar · 后端 120 秒内未就绪”。
- 运行记录列表显示每次的就绪用时。

### 2.6 不做

HTTP 探测（会向业务服务发请求，可能有副作用）；就绪后的持续健康检查；按就绪顺序启动依赖服务；就绪超时自动停止或重启；正则匹配。

## 3. 给 AI 的日志摘要

### 3.1 内容

对一次运行（服务或任务）生成确定性的文字摘要，按字节预算（默认 8 KiB，最大 64 KiB）返回：

1. **错误块**：识别为错误的行，加上紧随其后的堆栈。错误行的识别规则是固定的，写入契约：
   - 含日志级别 `ERROR` / `FATAL` / `SEVERE`；
   - 行首是 `Exception` / `Error` 类名加冒号（如 `java.lang.IllegalStateException:`、`TypeError:`），或是 `Traceback (most recent call last):`、`panic:`。

   只因来自 stderr 不算错误：很多工具把正常输出写到 stderr。
2. **堆栈折叠**：保留错误标题、前 5 个调用帧、每个 `Caused by:` / `Suppressed:` 及其前 2 帧，其余折叠为“省略 N 行”。规则与原生程序的日志折叠一致。
3. **合并重复**：同一错误反复出现（标题中的数字归一化后相同），只保留第一次，并标注出现次数与最后一次的行号。连续完全相同的普通行也合并为一行加“×N”。
4. **末尾**：最后 20 行（同样折叠与合并）。

预算的分配顺序是：第一个错误块、最后一个错误块、末尾几行，然后按时间补其余错误块。放不下的内容如实标注“省略了 N 个错误块 / N 字节”。日志较早部分已被上限丢弃时也要标注。

这是文字压缩，**不是 AI 诊断**：管理服务仍然不调用任何模型，也不解释错误原因。

### 3.2 增量读取

摘要和普通日志都支持“从第 N 行之后”读取。agent 记住上次读到的行号，下次只看新增内容，例如修完代码、触发热重载之后，只看之后的输出。

### 3.3 用法

```bash
devpanel logs <project-id> --service backend --digest --json         # 当前运行的摘要
devpanel logs <project-id> --run <run-id> --digest --after-seq 1200  # 第 1200 行之后
devpanel logs <project-id> --service backend --after-seq 1200        # 普通日志也支持增量
```

`--wait-ready` 未成功时自动附带摘要（§2.4）。

### 3.4 界面

日志工具栏增加 **“复制摘要”**：复制与 CLI 文本输出相同格式的摘要，用户可以直接粘贴给任何 AI 对话。这是人把运行信息交给 AI 的最短路径。

## 4. 操作来源与动态

### 4.1 发起方

每个改变运行状态或配置的请求都记录发起方：

| 发起方 | 如何得知 | 界面显示 |
| --- | --- | --- |
| 你 | 原生程序发出的请求 | “你” |
| 某个 AI | CLI 请求，附带 agent 名称 | 名称本身，常见名称有友好显示（`claude-code` → Claude Code、`codex` → Codex） |
| 命令行 | CLI 请求，未附带 agent 名称 | “命令行”（可能是人在终端，也可能是没有设置名称的 AI） |
| DevPanel | 管理服务自身（例如重启后的恢复与核验） | “DevPanel” |

agent 名称由 CLI 的 `--agent <名称>` 参数或环境变量 `DEVPANEL_AGENT` 提供。推荐用户在 agent 自己的配置里设置这个环境变量（例如 Claude Code、Codex 的环境变量配置），这样每条命令都会带上，不依赖 agent 记得加参数。

**名称是自报的，不是认证。** 界面如实称其为“自报名称”，权限规则（§5）也不按名称区分。

### 4.2 记录在哪里

- 每次操作（启动 / 停止 / 重启 / 强制停止）：发起方。
- 每次运行：由谁启动；结束时如果是被要求停止的，由谁要求。由此 agent 可以确定地区分“用户在面板里停的”和“另一个 agent 停的”。现有 skill 的规则“`user-stop` 且不是你发起的”目前无法从契约判断，这一项补上了。
- 快捷操作与 Maven 运行：由谁启动、由谁取消。
- 配置变更（注册、更新、选项增删改）：由谁修改、改了什么（与注册冲突时相同的差异格式，敏感值一律遮盖）。

### 4.3 动态

每个项目有一条“动态”时间线（新 → 旧，每项目保留最近 500 条），汇总上述记录：

> 14:02 Claude Code 重启了 后端 · 成功 · 12.3 秒后就绪
> 13:58 Codex 修改了配置 · revision 7 → 8 · `services[0].command[3]`：`--port=8080` → `${port}`
> 13:40 你 停止了 前端（之后 AI 需要你同意才能再启动）

- 只记录、可查看，**不提供回滚**。v0.2 “不做选项历史版本”仍然有效：这里是“谁改了什么”，不是可恢复的版本库。
- 删除项目时一并删除。
- CLI 也可以读取（`devpanel activity <project-id>`）。agent 可以借此知道“用户刚改了哪些选项”，不去覆盖。

### 4.4 界面

- 服务行和服务检查器：显示当前运行“由 Claude Code 启动 · 3 分钟前”；已停止时显示“由你停止”。
- 项目检查器新增 **“动态”** 标签：时间线；配置变更条目可以展开差异；条目可以跳到对应运行的日志。
- 不为 AI 的操作发通知，避免噪音。现有“非用户主动结束才通知”的规则不变，“被 AI 停止”同样不通知。

### 4.5 不做

可信的 agent 身份（签名、令牌）；跨项目审计导出；从动态回滚配置。

## 5. 托管规则（由管理服务执行）

### 5.1 原则

- 规则只约束 **CLI 请求**，界面请求永远不受限：人是最终决定者。
- 规则**只能在界面上修改**。它不属于项目配置：AI 注册 / 更新项目时无法改它，将来仓库里的配置文件也无法给自己授权。
- 被拒绝时返回明确的错误码和原因，agent 应当把原因告诉用户，请用户在面板操作或明确授权，不尝试绕过。
- **这是防误操作的约束，不是安全边界。** 同一用户下运行的程序都能读取管理服务的 socket 和 token，恶意程序可以伪装成界面。v0.4 防的是守规矩但会犯错的 agent。

### 5.2 停止后暂停（默认开启）

- 你在界面上停止某个服务（或停止整个项目）后，这些服务进入 **“暂停”**：AI 的启动 / 重启请求被拒绝。
- 暂停在以下情况解除：你在界面上启动它；你在界面上点“允许 AI 启动”；AI 带 `--override-hold` 启动。
- `--override-hold` 只应在用户于当前对话中明确要求时使用（写入 skill）。管理服务允许它，但会在动态里醒目记录“Claude Code 越过了你的暂停”。这与 v0.2 选项的“覆盖用户值需要显式参数”是同一种设计。
- 管理服务重启后，暂停保留。
- 项目可以关闭这条规则。

### 5.3 锁定服务

- 你可以锁定某个服务（例如你正在手工调试它）。锁定后，AI 不能启动、停止、重启、强制停止它，**没有越过参数**。
- 锁定只能在界面上解除。

### 5.4 AI 强制停止

项目级开关：是否允许 AI 强制停止（发送 SIGKILL）。默认 **不允许**（用户已确认）。理由有两点：
- 强制停止是唯一可能造成数据损坏的操作；
- 现有 skill 本来就要求“停止超时后由用户决定”，在面板里多点一下就能完成。

### 5.5 AI 侧表现

- 被拒绝的目标结果为失败，错误码 `POLICY_DENIED`，附带原因：暂停 / 锁定 / 强制停止不被允许。
- 被拒绝的停止请求不参与“停止优先”（v0.1 契约 §4.2）：不会取消排队中的启动。
- 被拒绝的目标就是全部失败原因时，CLI 退出码为 12（新）；与其他结果混合时沿用 6（部分成功），由 agent 逐个查看。
- `devpanel status` 显示每个服务的暂停 / 锁定状态，agent 可以在动手前先看。

### 5.6 界面

- 服务行：暂停时显示“⏸ AI 需你同意”，悬停说明原因与时间，可直接“允许 AI 启动”；锁定时显示锁图标。
- 服务右键菜单：锁定 / 解锁。
- 项目设置新增“AI 权限”分区：停止后暂停（开关）、允许 AI 强制停止（开关）、已锁定的服务。

### 5.7 范围与不做

- v0.4 只约束服务的启动 / 停止 / 重启 / 强制停止。快捷操作、Maven、选项不在本版规则内。选项已有 v0.2 的覆盖保护；Git 写操作本来就只允许界面发起。
- 不做：**审批请求**，即 AI 发起、人在面板点“批准”后继续执行，留到下一版视需要再做；按 agent 名称区分权限（名称是自报的）；更强的客户端认证（例如只有原生程序持有的凭据）。

## 6. 安装与分发

DevPanel 是开源项目，**不做签名、公证或包管理器分发**。用户在 GitHub 上自行下载使用。本节不涉及契约变更。

| 要求 | 说明 |
| --- | --- |
| 两种获取方式 | ① GitHub Releases：每个版本附一个 App 压缩包（本机 ad-hoc 签名）；② 按 README 从源码构建 |
| 下载即可运行 | Releases 的 App 内含管理服务（含 Node 运行时或单文件可执行）、原生采样辅助进程和 CLI，用户**不需要**另装 Node，也不需要源码仓库。从源码构建时仍需要 Node 与 Xcode 工具链 |
| 首次打开 | 未签名 App 会被 macOS 拦截：README 写明放行步骤（系统设置 → 隐私与安全性 → 仍要打开），不引导用户关闭系统安全功能 |
| 安装 CLI | 首次打开时引导，可跳过：把 `devpanel` 与 `devpaneld` 链接到用户选择的目录（默认 `~/.local/bin`），显示将写入的路径，目标已存在时先展示并询问，不改 shell 配置文件 |
| 登录时启动管理服务 | 可选项，默认关闭；沿用现有 `daemon install` 的语义 |
| 卸载 | README 写明：停止管理服务 → 删除 App、CLI 链接、登录项 → 数据目录是否保留由用户决定 |
| 升级与迁移 | 沿用 `~/Library/Application Support/DevPanel` 数据目录，新版本读取旧数据；从现有手工稳定版（`~/.local/share/devpanel/stable`）迁移的步骤写进文档。**升级由用户自己执行**，开发与验收不碰用户的稳定版 |
| 不做 | 签名与公证；Homebrew 等包管理器；自动更新；Linux / Windows 安装包（管理服务与 CLI 保持跨平台可构建，但不承诺支持） |

| 提案 | 内容 | 依赖 |
| --- | --- | --- |
| v1.3-A 就绪 | `ServiceConfig.ready`、`RunSummary.ready`、等待就绪路由、CLI `--wait-ready` 与启动报告、退出码 11 | 启动报告中的摘要依赖 B；B 未接受时退化为末尾日志 |

| v1.3-D 托管规则 | 项目规则、暂停 / 锁定、`POLICY_DENIED`、`--override-hold`、退出码 12 | 依赖 C（暂停要知道停止是谁发起的） |
| 安装与分发 | 无契约变更 | 无 |

建议的实现顺序是 C → D，与 B → A 并行；安装与分发独立进行。契约已生效，见 `contract/api.md` §13–§16。

**同步要更新的非契约文档**：`skills/devpanel/`（`--wait-ready`、`--digest`、`DEVPANEL_AGENT`、退出码 11 / 12 的处理、接入时登记就绪条件）；`devpanel project rules` 输出的规则文本。

## 9. 验收要点

| 场景 | 必须观察到的结果 |
| --- | --- |
| 日志就绪 | Spring Boot 服务登记 `Started … in`，`restart --wait-ready` 在该行出现后返回 0，报告含用时与行号；界面显示已就绪 |
| 端口就绪 | Vite 服务登记 `${port}`，监听后返回 0；改选项值后，下次启动按新端口判断 |
| 就绪失败 | 编译错误导致进程退出：退出码 1，报告附摘要，第一个错误块就是编译错误；超时：退出码 11，服务仍在运行、未被停止 |
| 未配置就绪 | 退出码 0，报告标“未配置”，stderr 有提示 |
| 管理服务重启 | 已就绪的保持已就绪；等待中的运行在能续接日志时继续判断，否则为“未知”（当前实现无法接回旧管道，因此为“未知”，属已知限制） |
| 摘要 | 同一异常重复 50 次只出现一次并标注次数；长堆栈被折叠且保留 `Caused by`；超出预算时如实标注省略；`--after-seq` 只含新增行 |
| 复制摘要 | 界面复制内容与 CLI 文本输出一致 |
| 发起方 | 设置 `DEVPANEL_AGENT=claude-code` 后启动：服务行显示“由 Claude Code 启动”；不设置时显示“命令行”；界面停止后，`status --json` 能看出停止由界面发起 |
| 动态 | 启停、配置修改、选项修改、任务运行与取消都出现；配置差异中敏感值被遮盖；删除项目后动态一并删除 |
| 暂停 | 界面停止后，CLI `start` 得到 `POLICY_DENIED`（退出码 12）且未启动进程；`--override-hold` 可启动，动态有醒目记录；界面“允许 AI 启动”后 CLI 正常启动；管理服务重启后暂停保留 |
| 锁定 | 锁定服务的 CLI 启动 / 停止 / 重启 / 强制停止全部被拒，界面操作不受影响；被拒的 CLI 停止不取消排队中的启动 |
| 强制停止规则 | 不允许时 CLI `force-stop` 被拒，界面可以执行 |
| 规则只能由界面修改 | CLI 修改规则得到 `FORBIDDEN_CLIENT`；`project update` 无法写入规则 |
| 安装 | 一台没有 Node、没有源码仓库的干净 Mac：从 GitHub Releases 下载、按 README 放行首次打开、安装 CLI、注册项目、启动、卸载全流程走通；按 README 从源码构建也能走通 |
| 资源 | 就绪检查只在等待期间进行，就绪后零额外开销；动态与摘要只在请求时计算；空闲资源与 v0.3 同条件对比 |

## 10. 决定

已确认（2026-10-21）：
1. 接受契约提案 v1.3-A ~ v1.3-D。
2. AI 强制停止默认 **不允许**（`agentForceStop = 'deny'`）。
3. 允许 `--override-hold` 越过暂停，在动态中醒目记录（§5.2）。
4. 开源项目，不做签名、公证与包管理器分发，用户从 GitHub 下载（§6）。
5. 实现分工沿用 v0.3：Codex 实现前后端，Claude 负责设计与 review；任务说明见 `prompts/codex-v0.4.md`（2026-10-22）。

待确认：
1. **名称**：Releases 与 App 名称与改名决定相关，公开发布前确定。
2. **LICENSE**：开源许可证由用户选择。
