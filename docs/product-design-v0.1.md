# DevPanel｜本地项目运行面板
## 产品设计 v0.1 · 2026-10-20

> DevPanel 是暂定名称。本文用于交给当前 IDE 工作区中的开发 Agent，先形成具体界面与工程方案，再据此实现。
>
> 本版本以用户最新要求为准，替代此前较宽泛的产品构想：只做项目接入、启停、日志、CPU/内存查看，以及供外部 AI 使用的同一套操作入口。Maven 面板、验证能力、任务中心和内置 AI 均不在首版范围。
>
> 本文没有检查任何目标仓库；示例项目、路径、命令和界面数字均为说明性内容，不代表真实环境，也不代表产品已经实现。

## 1. 一句话定位

**一个由 AI 配置、由人和 AI 共同操作的轻量本地项目运行面板。**

代码仍在用户原来的 IDE / Agent 中开发。新项目出现后，用户告诉 AI“把这个项目加入面板”；AI读取项目实际启动方式并完成注册。之后，不论用户点击按钮还是 AI 发起操作，都由同一个本地管理服务运行项目。用户始终能在面板中看见对应日志、资源占用，并停止它。

产品不是轻量 IDE，不是新的 Agent 聊天应用，也不是只显示端口的监控器。

## 2. 用户为什么需要它

当前阻力是：代码主要交给 Agent 修改，却仍为启动、停止、看日志打开完整 IDEA；改用终端后，运行入口、日志和进程容易分散。

本产品解决三个具体问题：

| 问题 | 产品承诺 |
| --- | --- |
| 新项目每次需要找目录、命令和环境参数 | AI配置一次，面板长期保存，也可手动编辑 |
| AI启动的服务不在自己的可控界面里 | AI与界面使用同一运行管理入口，不各自创建进程 |
| 不清楚哪个项目在运行、占用多少资源 | 按项目/服务显示实际状态、日志和CPU/内存 |

不承诺验证业务是否正确，不判断AI是否写好了代码，不对日志进行AI诊断。

## 3. 首版范围与默认前提

首版按单人、本机使用设计，以macOS为优先目标。是否采用桌面壳、原生窗口或现有本地Web界面，交给下一位Agent结合真实仓库决定；日常运行不能依赖先打开IDE。

| 必须有 | 具体边界 |
| --- | --- |
| 项目管理 | 添加、编辑、移除本地项目；项目内允许一个或多个服务 |
| 服务控制 | 项目级/服务级启动、停止、重启，显示实际执行结果 |
| 对应日志 | 实时stdout/stderr、搜索、复制、最近运行日志 |
| 资源占用 | 项目和服务的CPU、内存；运行时长作为辅助信息 |
| AI操作入口 | CLI与界面共享管理服务；能够注册、更新、查询、启停、读日志和资源 |

Maven可以作为后台服务的启动命令，例如项目实际使用的Spring Boot启动方式，但不提供Maven面板、生命周期树或通用构建任务管理。

只支持由面板启动并管理的本机前台进程。容器、远程主机、外部守护进程和现有进程接管不在首版范围。不得把Docker客户端的CPU/内存冒充容器资源。

## 4. 核心对象：项目、服务、一次运行

### 4.1 项目 Project

项目对应一个明确的本地根目录，例如一个代码仓库。包含名称、规范化根路径、稳定ID，以及服务配置。

同一根目录重复注册不能生成重复项目；同名但不同目录允许存在，界面必须提供路径区别。移动目录可修改路径，不要求删除重建。首版不专门管理Git分支或worktree。

### 4.2 服务 Service

服务是项目里一个独立的长期运行单元，例如后端、前端、Python服务。至少包含名称、稳定ID、工作目录、可执行程序与参数、必要环境配置。

一个项目只有一个服务时，界面弱化这一层：点项目就直接看该服务日志，不增加多余跳转。多个服务时，允许分别启停，也能一次控制整个项目。

不要把前后端塞进一个带`&`的复合启动命令；应登记成两个服务，使日志、停止范围和资源归属明确。

### 4.3 一次运行 Run

每次真正创建新的受管进程，产生新的运行ID。记录项目/服务ID、使用的配置版本、开始/结束时间、进程身份、退出结果和日志位置。

服务重启后，旧日志与新日志必须能够区分。面板重新打开不应创建新运行。

## 5. 三条核心用户流程

### 5.1 用户让AI接入新项目

用户在原来的编程Agent中说：“把当前项目加入DevPanel。”

AI读取当前仓库的启动脚本、目录、所需工具与环境配置，识别需要运行的服务。它不能照搬本文示例命令，不能把终端后台启动当成注册成功。

AI通过CLI提交项目配置。管理服务保存后返回稳定项目ID、服务ID和配置版本；已打开的面板自动出现该项目。

注册本身不执行启动命令。用户只要求“加入面板”时，到注册完成为止；明确要求启动时，AI再通过同一入口启动。

### 5.2 用户自己日常控制

用户打开面板，看到项目列表与运行数量。选中项目即看到日志、服务状态和CPU/内存。点击启动、停止或重启后，按钮与结果按真实进程状态更新。

用户切换项目、关闭窗口，不影响已运行服务。再次打开时重新连接管理服务并恢复状态和日志。

### 5.3 AI后续启动或重启

AI先按项目ID查询状态，再通过CLI请求启动或重启。管理服务负责创建进程、收集日志和资源，面板同步显示变化。

若已经运行，普通“启动”返回已运行，不产生第二份进程。若管理服务不可用，AI应报告问题，不能悄悄退回`nohup`、`&`、其他进程管理器或Agent临时后台任务。

用户在面板发出的停止应取消尚未完成的启动/重启操作。首版没有自动重启、自动恢复业务服务或持续拉起策略。

## 6. 界面与信息架构

### 6.1 整体方向

借鉴用户所说的Agent面板的组织习惯：左边持续可见的项目列表，右边当前项目的工作区。借鉴的是组织方式，不是复制某个版本的截图。

主窗口只承担一个核心场景：选项目 → 看运行情况 → 操作。

不设置欢迎仪表盘、任务广场、聊天输入框、文件树或独立“监控中心”。资源信息与日志同屏，避免为一个CPU数字再进入新页面。

### 6.2 左侧项目列表

顶部是“添加项目”。列表项显示项目名、简洁状态、运行服务数，例如“2/2运行”。项目总CPU/内存可放在第二行；空间不足时优先保留名称和状态，资源在主区完整显示。

列表不因状态刷新自动改变排序，避免用户点击时目标移动。点击项目只改变查看对象，不隐式启动、停止或切换运行配置。

列表底部保留本地管理服务连接状态。仅靠颜色不足以区分失败/停止，必须有文字或图标标签。

### 6.3 项目工作区

从上到下安排：

| 区域 | 内容 |
| --- | --- |
| 项目标题区 | 名称、简短路径、运行数量；启动/停止/重启；配置入口 |
| 项目资源摘要 | CPU、内存、统计完整性；多服务时为受管进程去重后的合计 |
| 服务区 | 名称、状态、CPU、内存、运行时长、单服务操作 |
| 日志区 | 默认展开、占据主要空间；服务选择、搜索、跟随滚动、复制 |

只存在一个服务时，避免同时出现两套相同的控制按钮和资源数字；将服务操作合并到项目标题区。

多服务时，默认选中上次查看的服务，首次进入选第一个服务。首版不做跨服务合并日志，保证日志归属和先后语义清楚。

### 6.4 添加/编辑项目

使用一个普通配置对话框或侧栏。必填内容只有项目名称、根目录和至少一个服务；服务必填名称、工作目录、启动程序/参数。环境变量等放在展开区。

提供“添加服务”。编辑与AI注册落到同一数据模型，不能存在UI能添加但CLI不能添加、或CLI字段在UI完全不可见的情况。

配置命令允许查看和复制，但环境中的敏感值默认隐藏。

### 6.5 视觉约束

紧凑但不过度拥挤；使用原生窗口习惯、克制的状态颜色、等宽日志。正常运行不持续播放动画。按钮与日志文字不能为了拟态Agent应用而失去可读性。

不把菜单栏集成作为首版阻塞项；先把主窗口和后台管理做可靠。

## 7. 启停行为契约

### 7.1 启动

服务未运行时，根据保存配置启动；已运行时返回现有运行ID。按钮连点、UI与AI并发启动也只能产生一份服务实例。

项目级启动只启动未运行的服务，按配置顺序发起，不等待业务健康就绪；一个服务失败不自动关闭其他已成功运行的服务。最终显示逐服务结果和“部分运行”，不能只显示总体成功。

命令必须是前台运行方式。`nohup ... &`、`docker compose up -d`、自行脱离管理范围的启动方式不属于首版支持契约；不要用命令退出码0推断后台服务仍在受管运行。

### 7.2 停止

停止对象是该次运行拥有的进程范围，不只是最外层Shell或Maven进程。应优先正常终止，并等待退出确认。

默认正常停止等待上限建议10秒。这是产品默认值，不是对所有程序关闭耗时的承诺。超时后显示“尚未停止”，提供明确的强制停止操作；发送了信号不等于已经停止。

不能使用全局`killall java`、按进程名批量结束、或看见端口占用就直接杀进程。只能对可核验属于本次运行的进程操作。

### 7.3 重启

重启必须先完成旧运行停止，再开始新运行。旧进程无法确认停止时，不启动新进程；不能用换端口的方式掩盖重复运行。

首版重启只重新执行保存的启动命令，不附带自动构建、测试或业务验证。

### 7.4 并发与用户停止

单服务变更操作需串行化，且有可取消的操作ID/版本。UI停止优先取消尚未结束的启动、重启和排队请求；旧请求不能稍后把服务再次拉起。

Agent规则要求：发现最新操作是用户主动停止时，终止当前自动启动/重启流程，不循环重试。用户后来明确要求启动时，可以查询最新状态后发起新的请求。

这是一套协作规则与受管请求的一致性保证，不是操作系统级权限隔离。具有同用户Shell权限的Agent仍可能绕过工具；不能声称写入规则文件就从技术上禁止了这种行为。

### 7.5 状态与文案

| 状态 | 含义 |
| --- | --- |
| 未启动 | 没有运行记录 |
| 启动中 | 正在创建受管进程 |
| 运行中 | 可核验受管进程仍存在；不代表HTTP或业务健康 |
| 停止中 | 已请求停止，等待进程退出 |
| 已停止/已退出 | 确認运行已结束；区分主动停止与程序自行退出 |
| 异常 | 无法启动、非预期失败退出或停止失败，展示原因/退出信息 |
| 状态未知 | 管理连接中断或无法核验，不能冒充已停止或运行正常 |

正常退出码0可显示“已退出（0）”，不是“验证通过”。没有健康检查模块，不显示“服务健康”“业务就绪”等结论。

## 8. 日志契约

日志来自受管服务的stdout/stderr，包含其正常继承输出的子进程。首版不自动解析应用自定义日志文件，也不接入外部日志系统。

必须有实时追加、保留换行和异常堆栈、常见ANSI颜色、文本搜索、暂停/恢复自动跟随、跳到最新、复制选中文字。搜索范围标明是当前已加载内容，不宣称搜索全部历史文件。

用户向上滚动时暂停跟随，出现新日志只提示，不抢滚动位置。暂停显示不能暂停后台收集，更不能阻塞业务进程输出。

切换项目或服务不串日志；异步回包必须核对服务/运行ID。服务停止后仍能看最近日志。重启后默认新运行，并允许通过一个简单下拉查看保留的最近运行，不新增大型“历史中心”。

首版建议保留每服务最近3次运行，并设置服务级与全局日志字节上限；具体上限在工程设计中固定并注明。内存缓冲与单次返回量必须有上限，不能把完整日志一次装进界面。发生截断、轮转、采集中断时必须明确提示。

如果应用缓冲自身输出、暂时没有日志，应显示“暂无新输出”，不能伪造实时性。stdout和stderr合并后的顺序按采集顺序展示，不承诺复原跨流绝对发生顺序。

日志当作文本渲染，不能执行其中HTML或任意终端控制命令。首版无内置模型，不会自动发送日志给第三方。

## 9. 资源占用契约

### 9.1 只显示最需要的内容

| 指标 | 首版口径 |
| --- | --- |
| CPU | 受管进程范围CPU使用率之和；单个逻辑CPU满载记为100% |
| 内存 | macOS 受管进程 footprint 之和，显示 MiB/GiB；RSS 仅作明确标注的辅助/回退 |
| 运行时长 | 自该次运行开始计算 |
| 辅助信息 | 最近采样时间、采集是否完整；必要时可展开进程数量 |

不提供JVM堆、GC、线程火焰图、网络流量、磁盘I/O、系统级监控大盘或资源趋势历史。

### 9.2 统计范围

服务统计应包含该次运行的启动器与已核验属于它的子进程，并持续跟踪新子进程，不能只统计`mvn`/Shell而漏掉实际JVM或Node进程。

项目合计按进程身份去重后求和。绝不把机器上所有同名Java/Node进程算进项目，也不把外部已运行的数据库、Docker daemon等算入项目。

需要进程身份校验，而非仅保存PID；PID可能被复用。建议记录PID、创建时间以及平台可用的运行归属信息。[S4]

CPU按上述口径可能超过100%；不截断、不按百分比条默认限制到100%。其含义是占用超过一个逻辑CPU。[S3]

macOS 主内存指标为受管进程的 `ri_phys_footprint` 合计，包含系统计账的压缩/换出内存；不是 JVM 堆、RSS 或全机物理页去重后的净占用。任一进程不可读时不发布部分 footprint 合计。RSS 保留辅助语义；回退必须标明“RSS”，其共享页跨进程可能重复统计。两者都不是结束项目后保证释放的内存。[S4]

### 9.3 刷新与缺失值

有运行服务时，默认约2秒采样一次；停止后停止该服务采样。所有界面共享管理服务的采样结果，不能每开一个窗口就独立扫描一遍。

首次CPU采样尚不足时显示“采样中”；权限不足、进程信息缺失或连接断开显示不可用/部分数据，不得用0冒充。界面保留上一值时必须标明时间与已过期状态。

如果管理程序或采样器自身消耗很大，属于实现缺陷；不得为本功能引入完整监控平台。

## 10. 配置与环境：同一套事实

配置的权威来源是本地管理服务保存的项目配置。UI和CLI均通过同一个服务创建、编辑和读取。

AI可提交JSON配置文件，但它只是导入载体；首版不同时维护一个仓库YAML和一份独立数据库并让两者各自生效。修改导入文件不会默默改变运行配置，必须明确提交更新。

示例仅用于说明字段，AI必须按实际项目调整路径、工具与参数：

```json
{
  "schemaVersion": 1,
  "name": "示例项目",
  "root": "/absolute/path/to/project",
  "services": [
    {
      "id": "backend",
      "name": "后端",
      "cwd": "backend",
      "command": ["mvn", "spring-boot:run"],
      "env": {}
    },
    {
      "id": "frontend",
      "name": "前端",
      "cwd": "frontend",
      "command": ["npm", "run", "dev"],
      "env": {}
    }
  ]
}
```

`cwd`相对于规范化项目根目录解析；程序与参数分开存储，避免路径空格和转义问题。确需Shell时明确指定Shell程序及参数，不能默默把所有字段拼接为命令字符串。

AI注册时检查项目实际使用的Wrapper、工具路径、JAVA_HOME等；面板不负责安装JDK、Node、Maven、下载依赖管理器或自动修改系统环境。

执行环境从管理服务与显式服务配置构造，不随发起请求的某个终端环境悄悄变化。优先显式保存必要工具路径与环境，使UI与CLI结果一致。命令查找受PATH配置影响，不能假定GUI启动环境天然等于用户交互终端。[S1]

环境秘密不得进入项目共享规则文件或普通状态返回。默认隐藏敏感值；本地配置与IPC凭证使用仅当前用户可访问的权限。CLI展示命令与日志时同样需要考虑泄露风险，自动隐藏不能保证日志绝对无秘密。

注册/保存配置只做字段、路径和必要配置校验，不执行命令。配置来自新项目时，应让用户或获授权的Agent明确发起第一次运行，不做“导入即执行”。

运行中修改配置只影响下次启动，展示“下次启动生效”；当前运行保留原配置快照。不能保存配置后偷偷重启服务。

## 11. UI与AI使用同一管理核心

### 11.1 必要结构

UI与CLI都是客户端。本地管理服务是唯一的受管进程创建与控制入口，同时提供状态、日志、资源和配置。

CLI不是另一套后台脚本：不能自己执行项目命令再把PID报给UI。前端窗口也不能独立维护另一份“正在运行”状态。

管理服务应独立于UI窗口和AI会话存活。CLI请求结束、Agent停止输出、窗口关闭，不应结束项目，也不应失去其日志。

进程持续运行与日志采集取决于会话、进程组、文件描述符等生命周期安排；单独设置“后台运行”并不足以自动得到完整托管。[S2] 具体方案由工程设计明确，不能只做UI演示。

### 11.2 CLI能力契约

以下是计划中的接口形式，不是已经安装或可用的命令。最终命令名可调整，但语义必须保留：

```bash
# 注册项目；只注册，不自动启动
devpanel project register --config /path/to/project.json --json

# 查项目与当前状态
devpanel project list --json
devpanel status <project-id> --json

# 更新已存在配置；携带已读取的配置版本，避免静默覆盖
devpanel project update <project-id> --config /path/to/project.json --if-revision <revision> --json

# 项目级或服务级控制
devpanel start <project-id> --json
devpanel stop <project-id> --service backend --json
devpanel restart <project-id> --service backend --json

# 读取日志；follow模式为持续流，普通模式有限返回
devpanel logs <project-id> --service backend --tail 200
devpanel logs <project-id> --service backend --follow

# 查看资源
devpanel stats <project-id> --json
```

服务级与项目级控制均需支持；CLI还需提供与UI同义的项目移除能力，运行中移除应拒绝，不暗中停止或删除源文件。

重复注册相同根目录且配置相同，返回现有项目。配置不同时返回差异/冲突，要求显式更新，而不是注册接口静默覆盖。更新不能误删此次未授权删除的其他服务。

CLI使用稳定ID定位，项目名称仅用于显示；禁止在有重名时猜测目标。结构化输出需区分请求已接受、正在执行和最终完成，返回真实当前状态、运行ID/操作ID及错误原因。

长操作可以返回操作ID并提供查询方式；开发设计须定义完整闭环。不能返回一次HTTP成功或退出码0就表示业务进程已成功启动/停止。

所有控制接口都需处理并发与重复请求。重要错误应有稳定错误码，例如项目不存在、配置冲突、命令不存在、目录不可用、停止超时、状态无法核验、管理服务不可达。

### 11.3 Agent协作规则

为每个被接入项目提供一段可复制的规则，并由获授权的Agent合并到项目现有规则文件，不能覆盖整个文件。Codex可以通过AGENTS.md读取项目约定。[S5]

建议规则内容：

```text
本项目的长期运行服务统一由DevPanel管理。

项目ID：<注册后返回的真实ID>

启动前先查询DevPanel状态。启动、停止、重启、查看运行日志和资源，
使用DevPanel CLI，不另用nohup、&、tmux或Agent临时后台任务启动同一服务。

DevPanel不可用时报告问题，不绕过它启动项目。
不要接管或结束不属于本项目受管运行的进程。
用户主动停止后，结束当前自动启动/重启流程，不自行循环重试。
用户明确重新要求启动时，读取最新状态后通过DevPanel发起新的请求。
修改运行配置应更新已注册项目，而不是注册一个重复项目。
```

规则只约束本项目的长期运行服务，不把普通代码编辑、单次Shell检查等都扩展成面板功能。

首版不需要MCP和内置LLM。CLI已经能承担目标工作流。后续增加其他入口时也必须复用同一管理核心。

## 12. 生命周期、异常和安全边界

### 12.1 关闭窗口与退出

关闭窗口仅隐藏/关闭UI，管理服务与项目继续运行；首次关闭给出明确提示。重新打开恢复连接，不重复启动项目。

“彻底退出”需明确处理运行项目：有项目在运行时，允许取消退出，或用户明确选择“停止所有受管服务并退出”。停止失败则报告，不假装完成。不能把整个进程生命周期绑定在渲染窗口或某次AI工具调用上。

第一版不默认开机启动业务项目。系统重启后恢复项目配置和已有日志，但项目保持停止，待用户或AI明确启动。

### 12.2 管理服务故障

UI断连时显示状态过期/未知，并禁用不可能成功的操作；CLI也返回真实失败。

管理服务重启时核验已记录的运行身份，能够可靠恢复的再恢复；不能只按旧PID“接管”。无法核验时显示管理中断/需要处理，阻止重复启动同一服务，保留可提供的运行信息。

首版不承诺从任意管理进程崩溃、日志句柄丢失或外部daemon化中无损恢复；必须显露缺口，不能用假“已停止”隐藏残留进程。

### 12.3 端口与外部进程

无需额外端口扫描仪或进程浏览器。端口占用错误原样保留在失败原因/日志中；若配置了预期端口，可作辅助检查，但端口号不成为进程归属证明。

首版不接管IDE或其他终端已经启动的项目。需要纳入面板时，先由用户处理原运行，再由面板重新启动。

### 12.4 本地接口

优先使用当前用户专有的本地IPC。若采用HTTP，只监听回环地址，并设置本地认证、来源检查及必要的跨站请求防护，不能仅凭“localhost”认为安全，更不能默认监听0.0.0.0。

本工具拥有执行已注册命令的能力；不自动接受不可信网页、仓库文件或日志文本里的操作指令。导入配置不等于执行授权。

## 13. 轻量要求

没有账户、云同步、模型调用、代码索引、整仓持续扫描、插件市场或监控大盘。日志与资源采集有边界，停止项目后释放相关采集与订阅。

优先复用当前仓库的UI与工程基础，不为了“正式架构”增加不必要的数据库服务、消息队列、容器或大型后端框架。

工程交付应报告面板及所有辅助进程的实际空闲CPU/内存，不能只统计前端窗口，或把被管理的Java/Node进程算作面板本体。具体指标目标在检查技术栈后制定并测量，不在未测试前承诺固定资源值。

## 14. 明确不做

首版不做Maven面板、通用构建任务中心、测试/验证中心、业务健康检查、AI诊断包、AI聊天、自动修复、调试器、代码编辑、Git/worktree管理、数据库客户端、容器/远程主机管理、自动端口改写、服务依赖编排、自动重启、复杂监控图表、团队协作与云端功能。

不读取或反编译IDEA来实现本需求；本版不需要IDEA内部项目模型，也不把Process Compose、Tauri、Electron、Swift或其他技术路线当成已经确认的选择。

## 15. 给下一位Agent的工程边界

先读取当前工作区的README、项目规则、技术栈、已有页面与本地执行能力。不要假定目标仓库是先前讨论的任何业务系统，不要使用本文示例路径创建真实注册记录。

如果存在明确可复用的面板应用，基于它增量设计实现；如果当前仓库是无关业务系统，不擅自塞入运行管理功能或重构全仓，应先说明结构不匹配与最小可行落点。

工程设计需要明确：界面布局、项目/服务/运行的数据模型、配置持久化、单一后台管理入口、CLI契约、进程树管理、日志限额、资源口径，以及生命周期。

复用现成进程管理引擎可以评估，但不能形成第二套事实来源。采用它必须说明如何满足资源统计、进程停止、UI与CLI一致性；采用与否均不应扩大产品范围。

不只实现Mock UI。真实命令执行、日志接入、资源采样与CLI互通是首版的一部分。

## 16. 开发验收标准

以下用于验收面板本身的实现，不是新增“产品验证中心”。

| 场景 | 必须观察到的结果 |
| --- | --- |
| AI注册一个项目 | UI出现同一项目与服务，注册没有偷偷启动 |
| 相同目录重复注册 | 不出现重复项目；不同配置需显式更新 |
| UI启动、CLI查询 | 相同运行ID与进程状态 |
| CLI启动、UI查看 | 能看到日志、CPU/内存，用户可停止该运行 |
| UI/CLI同时启动 | 同一服务只创建一个受管实例 |
| 一个项目两个服务 | 可分别启停、分别看日志；项目资源合计口径明确 |
| 命令不存在或目录错误 | 显示可理解的失败，不是持续假运行 |
| 程序自行退出 | 状态、退出信息和资源及时更新，日志仍可读 |
| 启动器产生子进程 | 统计包含实际服务；正常停止不残留受管服务进程 |
| 正常停止超时 | 显示未停止，并明确强制停止入口 |
| 停止发生在重启中 | 旧操作被取消，不被延迟启动请求重新拉起 |
| 关闭窗口或AI会话结束 | 项目继续受管运行；重开面板恢复同一运行 |
| 服务重启 | 新运行与旧日志可区分，不串日志 |
| 日志持续增长 | 内存/磁盘有上限，滚动不卡住，不阻塞项目输出 |
| 资源未采到或部分失败 | 显示采样中/部分/不可用，而不是虚构0 |
| 管理连接中断 | 显示过期/未知，不把旧状态当成实时事实 |
| 非受管同名进程 | 不统计、不停止、不自动接管 |
| 移除项目 | 不删除仓库文件；运行中要求先停止 |
| 本地运行接口 | 未经允许的外部请求不能执行项目命令 |

最重要的一条完整验收：

**让Agent注册并通过CLI启动一个真实项目 → 用户打开面板看到同一服务、日志和资源 → 用户在面板停止 → Agent查询确认已停止且受管进程已退出。**
